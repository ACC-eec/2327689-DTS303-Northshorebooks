# DTS303 — Northshore Books

A Django prototype for a small bookshop moving its catalogue, its customer accounts and its order management online — built as the practical component of DTS303 Advanced Web Programming. The goal is not a finished retail product; it is a defensible first iteration of the "click-and-mortar" model that the brief describes, with each feature traceable to one of the ten practical requirements and each security control verifiable in the codebase.

---

## How to launch this site (for the marker)

There are two one-click paths. Pick whichever is easier.

### Option A — Local (Windows / Mac / Linux)

1. Open this folder in your editor (or any terminal).
2. Run the launcher:
   - **Windows**: double-click `start.bat`, or run `start.bat` from a terminal.
   - **Mac / Linux**: `chmod +x start.sh && ./start.sh`.
3. Wait while the script creates the virtualenv, installs dependencies, writes `.env`, runs migrations, creates the admin user, seeds sample books, and starts the server. Your browser opens to `http://127.0.0.1:8000` automatically.

The launcher uses **SQLite** by default (no MySQL setup, no Docker). Re-running it is safe — it skips work that's already done. For the strict-MySQL marking path, use Option B (Codespace) below — it brings up MySQL 8 automatically as a sidecar container.

### Option B — GitHub Codespace

If you'd rather not run anything locally:

1. From the repository on GitHub, click **`Code`** ▸ **`Codespaces`** ▸ **`Create codespace on main`**.
2. Wait two or three minutes while the devcontainer installs Python, brings up MySQL 8 as a sidecar, installs dependencies, runs migrations, creates the admin account, and seeds sample books.
3. When the terminal prints `Northshore Books is ready`, run `python manage.py runserver 0.0.0.0:8000` and click the forwarded-port prompt.

### Where to go once it's up

- **Site**: `http://127.0.0.1:8000/`
- **Admin login**: `admin` / `NorthshoreAdmin1234!` at `/admin/`
- **Interactive API docs**: `/api/docs/` (Swagger UI)

If either one-click path fails, the manual local setup is documented further down.

## Tech Stack

- **Backend**: Python 3.11+, Django 5.0.3.
- **API**: Django REST Framework 3.14.0.
- **Authentication**: session cookies for the website paths, JWT (via `djangorestframework-simplejwt`) for the API paths.
- **API documentation**: an OpenAPI 3.0 schema and a Swagger UI front-end, generated by `drf-spectacular`.
- **Database**: MySQL (`mysqlclient` 2.2.0). SQLite is also supported for local development with `USE_SQLITE=True`.
- **Frontend**: Django templates, hand-written CSS (no framework), and a deliberately small slice of vanilla JavaScript.
- **Configuration**: `python-decouple` 3.8 for environment variables.

## Features

- A public book catalogue — list and detail pages, no account required.
- A REST API for books — JSON, paginated, with admin-only write verbs.
- User registration and authentication — Django's own forms, not a hand-rolled clone.
- Order management — basket, submit, view-history-only after submission.
- A customised Django admin — staff can add and update books, and inspect orders.
- The OWASP Top Ten classics handled at the framework level (CSRF, XSS, session hardening) plus a handful of bookshop-specific protections (order tampering, ownership-check on order detail).
- An editorial UI inspired by the layout grammar of online bookselling.

## Manual setup (fallback)

If `start.bat` / `start.sh` aren't a fit (e.g. you want MySQL rather than the SQLite default), the same steps spelled out by hand:

#### 1. Create the virtual environment

```bash
python -m venv venv
source venv/bin/activate    # Windows: venv\Scripts\activate
```

### 2. Install the dependencies

```bash
pip install -r requirements.txt
```

### 3. Configure environment variables

Copy `ENV_EXAMPLE.txt` to `.env`:

```bash
# Linux / Mac:
cp ENV_EXAMPLE.txt .env

# Windows:
copy ENV_EXAMPLE.txt .env
```

Edit `.env` with:
- `SECRET_KEY` — generate a fresh one for production; never reuse the development key.
- Database credentials.
- `ALLOWED_HOSTS` — comma-separated.

### 4. Bring up MySQL

There are two routes — pick one.

**Option A — Docker (recommended; no system install).**

```bash
docker compose up -d
```

This starts MySQL 8.0 on `localhost:3306` with the `northshore_books` database already created. Credentials default to `root` / `northshore_root_pw` and can be overridden via `.env`. Stop with `docker compose down`; wipe the volume with `docker compose down -v`.

**Option B — Native MySQL.**

```sql
CREATE DATABASE northshore_books CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Then ensure `.env` has `USE_SQLITE=False` and the right `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`.

### 5. Run the migrations

```bash
python manage.py makemigrations
python manage.py migrate
```

### 6. Create a superuser

```bash
python manage.py createsuperuser
```

### 7. Run the development server

```bash
python manage.py runserver
```

Then open `http://localhost:8000` in a browser.

## API Endpoints

### Interactive documentation

- `GET /api/docs/` — Swagger UI; click-through, requests can be tried in the browser.
- `GET /api/redoc/` — ReDoc; quieter reference output.
- `GET /api/schema/` — the raw OpenAPI 3.0 schema (YAML).

### Authentication (JWT)

- `POST /api/auth/token/` — exchange `{username, password}` for an access and refresh token.
- `POST /api/auth/token/refresh/` — exchange a refresh token for a new access token.
- `POST /api/auth/token/verify/` — confirm an access token is still valid.

The access token is sent on subsequent requests as `Authorization: Bearer <token>`. Access tokens last thirty minutes; refresh tokens last a day and rotate on each use.

### Books API

- `GET /api/books/` — list (public, paginated).
- `GET /api/books/<id>/` — retrieve (public).
- `POST /api/books/` — create (admin only).
- `PUT /api/books/<id>/` — replace (admin only).
- `PATCH /api/books/<id>/` — update (admin only).
- `DELETE /api/books/<id>/` — delete (admin only).

### Filtering and pagination

- `?author=<name>` — filter by author.
- `?min_price=<number>` and `?max_price=<number>` — bound the price range.
- `?search=<query>` — search across title and author.
- `?ordering=<field>` — order by `title`, `author`, `price`, or `created_at`.
- `?page=<number>` — paginate (ten items per page).

### Example API requests

```bash
# List the catalogue.
curl http://localhost:8000/api/books/

# Search.
curl http://localhost:8000/api/books/?search=django

# Filter by author.
curl http://localhost:8000/api/books/?author=Smith

# Filter by price range.
curl http://localhost:8000/api/books/?min_price=10&max_price=50

# Obtain a JWT for an admin user.
curl -X POST http://localhost:8000/api/auth/token/ \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "password": "your-password"}'

# Create a book using the access token.
curl -X POST http://localhost:8000/api/books/ \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access-token>" \
  -d '{"title": "New Book", "author": "Author Name", "price": "29.99"}'
```

## Security Notes

The full security write-up — threat model, design choices, traceability matrix, manual test walk-throughs, and the adversarial pen-test pass — lives in [`docs/SECURITY.md`](docs/SECURITY.md). The architecture and UI style guide live in [`docs/DOCUMENTATION.md`](docs/DOCUMENTATION.md); the REST and JWT surface in [`docs/API.md`](docs/API.md). What follows is the short version.

### Implemented controls

1. **SQL-injection prevention.** Django ORM only — no raw SQL, no cursor-level execute, no string concatenation building queries.
2. **XSS prevention.** Auto-escape on every template variable. No `|safe` filter on user-controlled content anywhere in the codebase.
3. **CSRF protection.** `CsrfViewMiddleware` plus `{% csrf_token %}` on every state-changing form.
4. **Session security.** `HttpOnly`, `Secure` (under HTTPS), `SameSite=Lax`. Session keys cycle on login.
5. **Password security.** PBKDF2-SHA256 hashing, ten-character minimum, common-password blocklist, per-(IP, username) rate limit on the login endpoint.
6. **Authentication and authorisation.** `@login_required` on every order view; ownership check returning `404` rather than `403` on `order_detail`; `IsAdminUser` on API write verbs.
7. **Security logging.** Structured JSON to `storage/logs/security.log`.
8. **Input validation.** Allowlists for `ordering`, numeric checks on price, length caps on search.
9. **Order integrity.** Server-side recalculation at submit; price snapshots on `OrderItem` to preserve the price the customer agreed to.

### Where they live in the codebase

- Security settings: `config/settings.py`.
- Security logging: `config/security_logger.py`.
- CSRF tokens: every template that posts.
- Authentication: `accounts/views.py`.
- Authorisation: `orders/views.py`, `catalogue/api.py`.

## Running Tests

```bash
python manage.py test
```

The test suite covers the auth and authorisation paths most likely to break under adversarial input — 36 cases across the three apps, split between happy-path `tests.py`, adversarial `tests_security.py` files, a JWT/registration pen-test suite at `accounts/tests_pentest.py`, and a regression suite that asserts the security log actually emits the structured `event_type` / `ip_address` / `username` fields it claims to.

## Production Deployment

A production checklist, in roughly the order it should be ticked off:

1. Set `DEBUG=False` in `.env`.
2. Set `SESSION_COOKIE_SECURE=True` and `CSRF_COOKIE_SECURE=True` — both require HTTPS.
3. Update `ALLOWED_HOSTS` for the deployment domain.
4. Configure the production database credentials.
5. Serve static files via WhiteNoise or an nginx alias rather than Django.
6. Run under a production WSGI server — Gunicorn behind nginx is the conventional choice.
